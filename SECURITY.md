# Security

## Что нельзя публиковать

- Telegram bot tokens, HeroSMS API keys и секрет webhook-пути.
- Реальные Telegram ID администратора вместо переменной `ADMIN_ID`.
- `.env`, SQLite-базы, WAL/SHM, дампы и резервные копии данных.
- Адреса и пароли пользовательских почт, SMS-коды, тела писем и ссылки входа.
- Боевые логи, снимки кабинета провайдера, production fixtures и диагностические ответы с персональными данными.

`.env.example` содержит только пустые поля/шаблоны. Тесты используют синтетические данные. Не копируй каталог работающего экземпляра в репозиторий целиком: переносить можно только проверенные исходники и обезличенные тесты.

## Секреты в SQLite

База — **секретный файл, а не безобидная статистика**. Она может содержать:

- ключи пользователей и именованного админского пула;
- ключи, с которыми покупались SMS и email-активации;
- Mail.tm-пароли и токены;
- почтовые адреса, ссылки входа, номера и коды;
- контекст незавершённых покупок и отложенных отмен.

Для dotenv и БД используй права `0600`, отдельного пользователя сервиса и защищённый каталог. Ограниченные файловые права не заменяют шифрование резервных копий. Не удаляй старый ключ из recovery-данных до завершения связанных операций и не публикуй backup, даже если он называется иначе, чем `bot.db`.

## Runtime-границы

- Все покупки требуют действующего пользователя и явного подтверждения. Outlook-подтверждение связано с токеном текущей сессии; повторные/устаревшие нажатия не должны повторять покупку.
- HeroSMS legacy передаёт `api_key` в query string, поэтому логирование HTTP-клиентов ограничено уровнем WARNING. Не включай дампы полных HTTP-запросов.
- Диагностика email-покупки записывает HTTP-статус, типы фиксированных полей, статический этап и класс ошибки — не тело ответа, адрес или токен.
- Изменение админского ключа удаляет сообщение с секретом; в журнале используются маска/метаданные, не полный ключ.
- Ключи активаций сохраняются отдельно от текущих назначений пользователей: отмена/восстановление не должны внезапно работать от другого счёта.
- Неопределённый результат платного POST остаётся в durable intent. Не повторяй его автоматически и не присваивай пользователю последнюю покупку общего ключа.
- Ссылку Outlook проверяют как HTTPS-ссылку разрешённого Wolt-хоста. Новые домены/схемы нельзя разрешать просто по вхождению слова `wolt` в URL.
- Удаление почты проверяет владельца и состояние покупки SMS. `sms_buying` — причина сохранить запись даже после рестарта, пока результат не сверен.
- Подтверждённая отмена и возврат денег — разные утверждения. HTTP-успех, таймаут или локальная отметка не доказывают возврат.

## Webhook

Listener по умолчанию привязан к loopback и без `HERO_WEBHOOK_TOKEN` не запускается. В контейнере может слушать `0.0.0.0`, но порт хоста должен оставаться закрытым извне, кроме разрешённого HTTPS reverse proxy.

Секрет в `/hooks/herosms/<secret>` служит аутентификатором: **это не цифровая подпись payload**. Не публикуй полный URL в логах и скриншотах; не открывай весь listener через nginx. Используй длинный случайный секрет, TLS и при необходимости дополнительное ограничение сети. Чужой секрет получает `404`; повторная доставка SMS отсеивается в SQLite.

## Безопасные проверки

Используй `python scripts/run_tests.py`: runner задаёт синтетическую конфигурацию до импорта приложения, инициализирует временную БД, блокирует подключения к реальным БД и внешней сети. Для webhook-тестов допускается локальный ephemeral сервер.

Не запускай `bot.main()` ради тестов с боевым токеном: второй polling-процесс вызовет `409 Conflict`. Проверка реальной покупки — отдельная согласованная операция, не часть unit-тестов или CI.

## Сообщить об уязвимости

Не вставляй ключи, почтовые пароли, коды или ссылки входа в публичный issue/PR. Используй приватный канал связи с владельцем репозитория; если доступны private security advisories — GitHub → Security → Advisories → New draft security advisory.

Если секрет попал в публичный git, чат или лог, отзови/замени его. Удаление строки следующим коммитом не удаляет секрет из истории.
